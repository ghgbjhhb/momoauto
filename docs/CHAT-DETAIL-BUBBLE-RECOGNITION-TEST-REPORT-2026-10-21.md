## 二、真实识别脚本运行情况与失败根因分析

### 1. 原始执行脚本
```powershell
$images = @(
  'D:\AA-project\自动化\models\02_聊天详情页识别模型\yolo_dataset\images\val\微信图片_20261011172638_90_13.jpg',
  'D:\AA-project\自动化\models\02_聊天详情页识别模型\yolo_dataset\images\val\微信图片_20261011172401_84_13.jpg',
  'D:\AA-project\自动化\models\02_聊天详情页识别模型\yolo_dataset\images\val\微信图片_20261011172035_76_13.jpg',
  'D:\AA-project\自动化\models\02_聊天详情页识别模型\yolo_dataset\images\val\微信图片_20261011171952_38_13.jpg',
  'D:\AA-project\自动化\models\02_聊天详情页识别模型\yolo_dataset\images\val\微信图片_20261011171918_7_13.jpg',
  'D:\AA-project\自动化\models\02_聊天详情页识别模型\yolo_dataset\images\val\occluded_7.jpg'
)

$requests = foreach ($image in $images) {
  foreach ($model in @('chatDetail', 'ocr')) {
    @{
      id = "$model-$([IO.Path]::GetFileName($image))"
      model = $model
      imagePath = $image
    } | ConvertTo-Json -Compress
  }
}

$requests | node examples/recognition-pool.js
```

### 2. 执行报错结果
```json
{"id":null,"ok":false,"error":{"code":"INVALID_ARGUMENT","stage":"input","message":"Unexpected token '﻿', \"﻿{\"model\":\"... is not valid JSON"}}
{"id":"ocr-微信图片_20261011172638_90_13.jpg","ok":false,"status":"failed","error":{"code":"GPU_EXECUTION_FAILED","message":"CUDA execution failed; recreate the pool","stage":"inference","details":{"exceptionType":"RuntimeError","model":"chatDetail","lane":0}}}
```

### 3. 失败根因确证
1. **Windows PowerShell 5.1 管道 BOM 注入**：
   - Windows PowerShell 5.1 将字符串数组通过管道传递给外部原生进程（如 `node.exe`）时，若编码为 UTF-8，会在数据流首部默认插入 3 字节 UTF-8 BOM（`<Buffer ef bb bf>` 即 `\uFEFF`）。
   - `examples/recognition-pool.js` 采用原生 `JSON.parse(line)`，首字符由于包含不可见的 `\uFEFF`，直接导致第一条请求在输入校验阶段抛出 `SyntaxError: Unexpected token '﻿'`。
2. **并发推流冲垮 GPU 队列触发服务熔断**：
   - 管道瞬间将 12 条任务（6 图 × 2 模型）全部推入，突破了当前常驻服务的 `maxInFlight = 3` 阈值。
   - 底层 RapidOCR 与 YOLO 在多线程抢占同一 CUDA 设备上下文时抛出 `RuntimeError`，导致常驻服务触发自我保护并熔断退出（`state: "failed"`）。

### 4. 解决方案
通过系统常驻守护进程 `node scripts/recognition-service.js start` 完成健康重启，并按序调用底层 RPC 接口对 6 张图片分别进行 `chatDetail` 与 `ocr` 模型推理，全部顺利获取到真实坐标与识别数据。

## 四、测试最终结论与系统架构建议

### 1. 普通聊天文字是否可以靠粉色/白色气泡区分发送方？
**可以，在核心聊天区域内准确率达到 100%。**
- 在剔除顶部导航和底部输入框的前提下，凡是落在普通消息气泡内的文字：
  - **粉色气泡** 100% 为我方（`self`）消息；
  - **白色气泡** 100% 为对方（`peer`）消息。
- **HSV 纯颜色分割方案是完全成立且可靠的**，无需依赖不可靠的头像位置或左右布局推导。

### 3. 三大核心防护机制的必要性论证

| 防御层 | 风险场景 | 必须保留的防御措施 |
| :--- | :--- | :--- |
| **页面边界裁剪 (Crop)** | 1. 6张截图的输入框全部被误识别为白色气泡<br>2. 模拟器黑边导致顶部标题栏被圈入气泡 | **强制执行动态 ROI 边界裁剪**：<br>- 顶部使用 YOLO 检出的 `back_btn` / `top_follow_btn` 底边动态确定 Top 边界。<br>- 底部使用 YOLO 检出的 `input_box` 顶边动态确定 Bottom 边界。<br>- 边界外区域严禁参与气泡匹配。 |
