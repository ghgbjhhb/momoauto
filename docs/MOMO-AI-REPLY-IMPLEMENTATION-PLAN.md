> 编写日期：2026-10-19。项目：`D:\AA-project\自动化`。本文件是待执行的开发计划，不代表功能已经实现或通过实机验收。

## 1. 目标和完成定义

用户已拥有联系人识别、历史聊天采集和入库能力。本期在其上补齐：

```text
识别疑似新消息
  → 定位联系人并进入聊天
  → 确认页面类型与聊天对象
  → 读取最近消息，必要时向上补取到存档锚点
  → 与存档按消息顺序对齐，只保存真正新增的消息
  → 读取该联系人的历史对话和网页配置的系统提示词
  → 调用用户配置的 API，得到回复正文
  → 再核对对象、上下文、输入框
  → 模拟拼音按键、识别候选词、核对草稿、点击发送
  → 观察己方新增消息，保存结果，返回结构化状态
```

必须同时满足：不串联系人、不串设备、不丢真实重复发言、不重复处理同一批消息、不因发送超时而重复发送。视觉识别不能提供平台原生消息 ID 或送达回执，无法消除的歧义必须明确返回，不能假装可靠。

交付为可被后续中枢调用的**有界工具**：单次处理指定联系人，或者扫描并处理最多 N 个候选联系人，结束后返回。不在本期内部写无限循环。

### 3.3 明确区分三种模式

| 模式 | 手机操作 | 写业务库 | 外部 API | 真实输入/发送 |
| --- | --- | --- | --- | --- |
| plan，默认 | 不截图、不导航、不敲键 | 只读已有资料，不建库不迁移 | 不请求 | 禁止 |

## 5. 对外调用契约

### 5.1 有界工作流

建议导出 `runMomoAiReplyOnce(client, deviceId, options)`，支持：

- `contactId`：可选；指定时直接处理该设备已知联系人，否则进行有界扫描。
- `mode`：`plan | draft | execute`，默认 plan。
- `maxContacts`：默认 1；扫描候选和实际处理数量分别统计。
- `maxListPages`、`maxHistoryPages`、`timeoutMs`：单次硬预算。
- `initialPolicy`：初次启用处理策略，见第 7 节。
- `signal`、`operationId`：取消与追踪；operationId 不能代替服务端幂等校验。

目标设备使用后台真实 deviceId，不使用会随排序变化的“第几台”。配置由后台按 deviceId/accountScope 解析，不接收浏览器直接传入的库路径或权重路径。

建议把“扫描候选”“读取并合并”“生成回复”“发送回复”同时作为内部可独立测试/复用的函数，不把整个流程塞进一个数百行函数。

### 5.2 结果信封

沿用项目现有 `ok/status/operationId/deviceId/data/error` 思路，并增加：

- `data.outcome`：`no_new_messages | draft_ready | reply_observed | needs_baseline | needs_review | partial`。
- `data.contacts`：每个联系人独立的处理结果，不能用一人的成功掩盖另一人的失败。
- `data.newPeerCount`、`newSelfCount`、`overlapCount`、`historyCoverage`。
- `data.replyJobId`、`contextVersion`、`configRevision`。
- `data.sendState`：`not_started | send_attempted | input_cleared | own_bubble_observed | uncertain`。
- `data.coverage`：扫描页数、是否确认列表尾部、预算是否用尽，不能把预算耗尽报成全列表无新消息。
- `error`：`code/module/stage/retrySafe/retryable/details`，details 不携带明文密钥。
- `timings`：截图、各类识别排队/推理、对齐、数据库、API、输入和发送确认耗时。

`ok` 只表示这次工具是否按契约完成；上层必须看 outcome/sendState。识别失败不是 no_new_messages，输入清空不是 reply_observed。

### 5.3 纯 API 工具

`generateReply()` 的输入包括不可变配置快照、系统提示词、有序历史、触发消息 ID 范围、上下文版本和取消信号。

输出统一为回复正文及本地元数据：`text/provider/model/requestId/usage/finishReason/configRevision/contextVersion`。这些关联字段由本地代码绑定，不能信任模型自己返回或回显。

第一版只请求并接收一条纯文本回复，不要求模型 JSON 控制手机，不开放工具调用。协议层角色和值由适配器映射，不将未经校验的上游响应直接传给输入引擎。

## 6. 网页配置和 API 适配

### 6.1 网页字段

在现有 4318 页面增加“AI 回复”设置，只有必要字段、按钮、状态和错误，不加入“点击这里”“支持某功能”等说明性小字。

| 字段 | 要求 |
| --- | --- |
| API 协议与请求地址 | 首版接一个明确协议；地址由用户配置。完整 endpoint 与 base URL 二选一并固定含义，不能偷偷重复拼路径 |
| API Key | 后台保存；读取接口只回 hasApiKey 和屏蔽状态，不回原值 |
| 模型名 | 用户配置，不能假设模型一定支持某些参数 |
| 系统提示词 | 网页编辑、后台持久化；必须实际加入每次请求，不能只保存不使用 |
| 超时、最大输出、必要的生成参数 | 有范围校验；不支持的供应商参数不盲传 |
| 上下文策略 | 本期默认完整可用文字历史；超预算报错，不静默截断 |
| 首次处理策略 | 默认按既有存档与当前未读/新增证据处理；支持仅建立基线 |

先实现一个用户明确选择并核对官方协议的供应商适配器，保留统一接口。不在供应商尚未确定时宣称兼容所有 API；不要为等一个密钥阻塞本地模拟开发。

全局配置可作默认值，设备覆盖值只覆盖明确设置的项。每次保存增加 revision；运行中的任务使用自己的快照，不能前半段使用旧提示词、后半段使用新模型。

### 6.2 密钥与配置安全

- 密钥和配置保存在后台专用的忽略目录，例如 `.runtime/ai-reply/`，不放在 app/、源码、URL、浏览器 localStorage 或聊天库明文日志中。
- API Key 省略表示保留；清除使用明确操作；不能把屏蔽字符串覆盖为真实 Key。
- 不覆盖 `.env.local` 中原有云机配置；若复用配置文件，必须保留所有无关项并做原子更新。
- Windows 文件权限需实际核对，不能声称设置 mode=0600 就完成了 Windows ACL 隔离。
- 地址限制 http/https，拒绝 URL 内嵌凭据；远程默认要求 HTTPS。本地模型的 HTTP 地址只能在用户明确配置时允许。
- 密钥只发送给最终校验的供应商地址；禁止自动跨源重定向转发 Authorization。错误信息、供应商错误正文、请求日志统一脱敏。
- 保留现有本地 Host/Origin 守卫；此方案不等于已经具备对外售卖所需的用户鉴权和租户隔离。
- 配置/任务接口禁止缓存；前端通过 textContent 展示提示词、回复与联系人文本，不注入 innerHTML。

### 6.3 请求、响应和失败

1. 先校验配置、上下文和回复长度预算，再请求。
2. 默认非流式；拿到完整可验证回复后才进入打字，不边生成边发送。
3. 设请求与整体 deadline；用户取消后即使上游迟到返回，也不能继续打字。
4. 校验 HTTP 状态、响应类型、结构、正文、输出是否截断或包含未执行的工具调用。
5. 空白正文、内容拒绝、截断、超长和输入引擎不支持的字符分别返回状态，不静默裁剪或发送半句。
6. API 请求最多进行小次数重试，纳入全局预算；对 429 尊重 Retry-After，对鉴权失败、参数错误不重试。
7. 生成请求失败不得触发手机发送；重试生成也不得建立重复的回复任务。网络重试可能重复计费，记录上游 requestId 与 attempt。
8. API Key、模型或地址未配置时返回 CONFIG_INCOMPLETE；“测试连接”是显式的可能计费操作，使用固定非私人测试内容，不顺带发出手机消息。

HTTP 非幂等请求不得仅因超时而假定可以重试，见 [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。手机发送的禁重发规则另外按第 10 节执行，不与 API 重试混用。

## 7. 发现和读取真正的新消息

### 7.1 消息列表只用于发现候选

- 使用 SDK 高清源图 `source:'stream'`，关键动作使用新鲜帧，不用网页缩略图或浏览器截图。
- 同一帧的 page/chatList/OCR 结果绑定 screenshotId、尺寸、时间和连接 generation；任何必要识别返回 ok:false 都应失败。
- 保留模型已有 filterEdgeCards/首尾不完整卡片过滤和用户设置，不擅自关闭。
- 系统卡片、招呼入口、广告和最近在线区域不作为普通联系人。
- 候选依据包含未读提示、摘要/位置变化和持久化待处理任务。未识别出数字不能等同于未读数为零；现有 1–2 位 OCR 数字规则不覆盖红点和 99+，必须有 unknown 状态及对应测试。
- 摘要没有变化也不能证明无新消息，例如对方又发一次相同文字；需要未读信号及有界近期联系人复查。
- 不能固定点击“第几个卡片”。列表排序或滚动后重新定位，过期坐标全部作废。
- 扫描只覆盖预算内的列表范围，结果明确返回范围。纯视觉方案不是平台消息推送，不能声称知道屏幕外全部消息。

### 7.2 双层确认联系人

点击前保存预期 contactId、昵称原文、可用头像区域特征、来源帧与卡片位置。点击后必须同时确认：

1. 页面为 MOMO 聊天详情页，输入框和返回控件等证据成立。
2. 顶栏联系人信息与目标匹配，必要时结合头像区域与连续导航证据。

标题图像签名只能帮助判断发送过程中是否切换了对象，不是平台账号 UID。只匹配昵称也无法消除同名风险。昵称截断、同名歧义、头像不符或身份低置信度时返回 TARGET_UNVERIFIED/TARGET_MISMATCH，不写入该联系人的消息，不发送。

同机同名自动合并不在本期范围；不能因为“先不做身份系统”而取消对象确认。可以让该联系人进入人工绑定/复核状态。

### 7.3 最近消息读取

1. 核对并处理遮挡；无法确认安全关闭的弹窗停止，不猜关闭坐标。
2. 到达聊天最新端，使用连续稳定观察确认，而不是仅凭滑动次数或空 OCR 判断触底。
3. 解析可见消息，保留正文原文、发送方向、类型、时间原文、气泡/头像锚点、截图证据。
4. 向上补取，直到与已归档尾部得到唯一可靠对齐；每次滑动后重新截图识别。
5. 没有重叠则在 maxHistoryPages/timeout 内继续；预算耗尽返回 HISTORY_GAP，不把全部可见内容直接追加。
6. 找到存档锚点后不再遍历到历史顶部；但发送前必须重新回到最新端并核对。
7. 跨屏气泡、多行文字只在同一气泡证据下合并；不能仅靠距离把两条发言拼成一句。
8. 图片、语音、视频及无法理解的消息显式记录类型/占位和未支持原因；如果最新待回复内容依赖它们，默认转人工，不装作已经读懂。

### 7.4 首次启用与重启

- 已有归档：先把已归档内容导入 AI 的基线，不能把导入动作本身当新来信。随后与当前聊天对齐，归档之后新增的 peer 消息才进入候选批次。
- 默认首次处理策略：有当前未读证据，或已有持久化 pending 任务，或本工具运行期间明确观察到新增 peer 消息，才自动进入回复流程；仅仅“旧库没有这一行”不充分证明是新来信。
- 用户可选 baseline_only：本次只建立现场基线，不发送；不能在用户选择处理当前未读时擅自把刚采到的新来信全部吞进基线。
- 无归档联系人：返回 needs_baseline，安排受限的首次采集或等待人工启动流程 13；不得默认把整个多年历史当新消息回复。
- 基线建立和新来信之间的边界要通过前后观察对齐，不能在建基线过程中漏掉新来的消息；无法区分时明确转人工。
- 进入聊天可能清除未读角标。任务在此后失败，重跑仍应根据本地 pending 找到它，不能因角标消失而永久漏处理。

## 8. 增量去重与数据库设计

### 8.1 两种去重必须分开

**同一次滑动采集的拼屏**：相邻视口有几何位移，可以借用 chat-history.js 的后缀/前缀对齐思路。

**本次采集与此前归档的对齐**：归档跨时间、可能不同键盘高度和滚动位置，不能继续要求旧坐标与本次坐标一致，应比较有序消息及可信时间、气泡方向等证据。

推荐算法契约：

1. 按从旧到新形成观察序列；正文保留 rawText，匹配文本最多做明确的 NFC/换行规范化，不全局去空格、不删除标点、表情或数字。
2. 在有界归档尾部寻找与本次序列的连续有序重叠。发送方向、类型、正文和可信时间共同参与；时间缺失不能编造。
3. 一次单词/单条文本相等不足以证明同一条消息。优先使用多个不同内容的有序锚点；确实只有单条时，需要额外连续观察证据，否则返回歧义。
4. 所有满足条件的候选对齐均需评估；若存在多种合理新增条数，不可仅选最长重叠强行成功，应继续补屏或停止。
5. 只有被唯一对齐证明位于存档末尾之后的条目，才作为新增；观察中的旧消息不能再次追加。
6. OCR 模糊匹配只能用来发现“需要重读”的候选，不可直接改写历史文字或触发发送。持续不一致返回 OCR_INCONSISTENT。
7. 模块返回对齐起点、重叠长度、新增序列和证据，不自己持有数据库连接。

必须验证的例子：

- 存档 `[peer:你好, self:你好呀]`；现场 `[peer:你好, self:你好呀, peer:在吗]`：只新增“在吗”。
- 存档 `[peer:你好]`；现场再次稳定观察到两个独立“你好”气泡：不能按正文 Set 删除第二条；若仍不能确定它们与存档的对应关系，则补证据，不猜。
- 对同一现场截图重复识别十次：数据库与待回复任务数量不增长。
- 旧消息 OCR 从“你 好”变成“你好”：不能因为规范化碰撞就擅自吞字，也不能直接当成一条新来信。

### 8.2 兼容存储方案

推荐在每台设备原有 momo.sqlite 中**新增 AI 专用表和仓储**，不修改旧表的唯一约束，不把增量塞进 saveMessages。以下为逻辑字段要求，具体 DDL 在 P1 阶段确定并测试。

| 表 | 关键数据与约束 |
| --- | --- |
| `ai_conversations` | 本地会话 ID、deviceId、accountScope、旧 contactId、身份绑定状态、基线状态、legacy 来源水位、contextVersion |
| `ai_messages` | 稳定本地 messageId、conversationId、递增 seq、sender/type/rawText、时间原文、来源 legacy/live/bot_observed、证据引用、可信状态；UNIQUE(conversationId,seq) |
| `ai_reply_jobs` | jobId、conversationId、触发消息范围、inputDigest、contextVersion、configRevision、回复正文、状态、发送尝试、观察结果、错误和时间 |
| `ai_conversation_state` | lastObservedSeq、handledThroughSeq、最近列表证据、待处理批次信息；其中处理位置只作兼容记录，不作为单次调用跳过回复的条件 |
| `ai_schema_migrations` | 版本与已完成迁移；也可复用真正存在且兼容的项目迁移机制 |

关键约束：

- 本地 messageId 是随机/分配的记录身份，不是正文 hash，也不是平台消息 ID。
- 同一文本可以有多条不同 seq。content hash 只辅助对齐或追踪，不作为消息唯一键。
- AI 查询统一读取仓储里的有序视图；不能同时把旧表全文和已导入副本再拼接一次。
- 初次导入使用 `getMessagesByContact()` 的现有优先级，新格式完整序列优先；同一旧记录建立稳定来源映射，多次导入不重复。
- 导入历史建立基线，不创建回复任务。旧表重复丢失问题记录到 coverage，不伪造恢复。
- 旧流程 13 后续产生新归档时，仓储比较来源水位/修订；通过受控对齐更新，无法对齐标记需要 reconciliation，禁止直接又导入一遍。旧表和新表不能悄悄形成两个冲突事实源。
- 一次“合并增量、增加 contextVersion、更新观察游标、建立/更新待回复批次”在同一短事务完成；事务回调不能 await 网络/截图/模型。
- 生成及发送结果状态使用条件更新/CAS；旧版本任务不能覆盖新上下文。
- 同一会话最多一个有效待发送意图。新来信可合并或使旧草稿失效，但已 send_attempted 的任务先核验，不能直接另开一条发送。
- 新增 seq 通过事务分配；不能在事务外 MAX(seq)+1 后直接插入。
- 自定义路径需要校验设备归属；账号会话切换必须停止旧任务并重新绑定基线。当前缺少可验证账号信息时使用显式 accountScope，不能把云平台网页登录令牌当 MOMO 账号身份。

### 8.3 备份与回滚

迁移前用支持一致性快照的备份机制，或者在所有相关数据库连接和写任务关闭后再复制。不要在活跃写库时只复制主文件而忽略 WAL/并发状态。[SQLite 官方备份说明](https://sqlite.org/backup.html)

迁移只新增可回滚对象；停用新模块后旧流程仍可读取原表。验证完整备份可读和恢复步骤，不直接在真实库上做破坏性迁移测试。

## 9. 历史上下文与系统提示词

1. 先完成增量事务，再从同一 contextVersion 的稳定快照读取历史。
2. 本期默认携带**全部可用、已确认且有序的文字历史**，不是仅发最新一句，也不是擅自只取最近 20 条。
3. 对方发言映射为 user，己方真实发言映射为 assistant；历史己方人工发送也必须包含。待发送草稿不算已发生的历史消息。
4. 网页的系统提示词作为系统层内容加入一次。聊天中的“系统通知”、时间、昵称、OCR 识别到的指令不能升级成 API 的 system/developer 指令。
5. 新消息已经在历史里出现，就不再作为末尾额外 user 内容重复加入。触发批次另用本地消息 ID 范围关联。
6. 同一发送者的连续消息按原顺序保留；若供应商限制角色交替，由适配器在不丢内容和边界的前提下明确转换并测试。
7. 保留历史中的真实重复发言，不按 role+content 再次去重。
8. 系统时间提示、距离和媒体占位可作为低信任元数据表达，但不能伪造文字内容或精确日期。
9. 完整上下文超过模型预算时返回 CONTEXT_BUDGET_EXCEEDED，不静默丢历史。本期不强制开发摘要记忆；未来要加窗口/摘要，必须网页明确启用并显示覆盖策略。
10. 使用供应商可用的 tokenizer 或明确保守的预算校验，并为输出保留空间；中文字符数不能直接等于 token 数。
11. 最新内容是无法理解的图片/语音、关键 OCR 低置信度、历史存在影响回复的缺口时转人工，不把不完整输入伪装成完整会话。

可配置短暂合并连续来信的等待窗口；等待受整体 deadline 限制。API 请求期间再次收到来信，旧结果先置为 stale，重新读取、合并再评估；次数有上限，持续来信时返回 deferred/needs_review，不能无限生成。

配置改变、身份改变、检测到人工新发言，都应使旧草稿失效或暂停。不能因为 API 已经花钱返回，就强行发送旧答案。

## 10. 通用模拟输入与发送状态机

### 10.1 复用现有输入，不新增错误焦点路径

建议增加 `tools.sendChatMessage(text, options)`，至少接收经核对的 expectedPeer、contextVersion、jobId 和 execute 标志。调用前后保持同一设备操作所有权。

- 复用 ChatInput、prepareMessages、现有 SDK 按键与候选/草稿 OCR。
- 继续根据模型 2 的输入框位置判断键盘是否展开；中部已打开则不重复点击，底部才安全聚焦，模糊区停止。
- 输入前准备完整按键计划，验证其正文拼接等于回复原文。
- 不使用电脑窗口焦点、不直接粘贴中文、不盲选第一候选、不硬编码候选序号。
- 默认只支持已验证的单条普通文字；不支持的换行、表情或字符明确拒绝，不静默删除。
- 草稿必须逐步和最终核对；未知已有草稿不自动清空。失败留下的本工具草稿也需通过 job 归属和精确正文核验才能恢复，不能覆盖用户输入。
- 输入耗时较长时，在点击发送前再次检查当前最新消息、身份、任务/配置版本、遮挡及草稿。存在新来信则停止发送旧回复；已输入草稿保留并标记归属，按可验证的安全恢复处理。
- 所有动作前验证来源帧、尺寸、generation 和新鲜度；新工具按项目当前守则不超过 1000ms 的证据窗口重新核验，不把旧工具的 3 秒容忍默认为新工具安全阈值。
- 任何界面动作后旧坐标失效。禁止跨刷新/滑动复用发送按钮坐标。

### 10.2 发送任务生命周期

```text
pending → generating → draft_ready → preflight_verified
                                      ↓
                                send_attempted
                                 ↙         ↘
                      own_bubble_observed   uncertain
```

其他分支：生成/读取失败可在安全条件下重试；stale、cancelled、needs_review 独立记录，不能塞进成功状态。

实施规则：

1. 点击前持久化发送意图及预期正文、触发范围、发送前消息尾部锚点；持久化失败禁止点击。
2. 对同一 job 做条件状态更新，确认没有别的执行者已发送或取消，再下发一次点击。
3. 点击成功、输入清空、网络写入成功分别记录，不单独据此认定业务完成。
4. 发送后读取当前聊天，确认在发送前锚点之后新增了一条己方气泡，并与待发正文、方向、顺序对应；检测明确发送失败标记。
5. 匹配必须带位置/序列锚点，不能只在屏幕上找“历史里有同样一句话”。两次稳定观察可增强证据，但不是平台回执。
6. 观察成立时，原子保存己方消息并关联 job；`handledThroughSeq` 可以保留作历史记录，但之后的单次调用仍以当前最后一条消息为准，不用它跳过回复。再次读取同一气泡要通过对齐映射到同一 messageId，不新增副本。
7. 已尝试点击但无法核验、断连、取消、进程崩溃：标记 uncertain；恢复后先只读核验，绝不能从 typing 或 send 再跑一次。
8. 不能确定“肯定未执行”的情况，宁可进入人工复核；只有有证据证明未派发的动作才允许有限重试。
9. 取消/关闭后释放已按下的按键与触点，不回放未完成输入；若已有发送副作用，保留 uncertain，不把取消当成什么都没发生。

`own_bubble_observed` 只代表在当前账号界面观察到己方消息，`deliveryConfirmed` 仍为 false，不能声称对方已读或已收。

## 11. 设备占用与服务接入

### 11.1 同机串行，跨机有限并发

- 一台手机只由一个受管操作任务持有写权限。读取流程如果会导航/滑动，也必须持有设备占用。
- 复用一台设备的同一个 tools/control 会话，不每个步骤创建一次连接。
- 多台设备的识别继续借用公共 GPU 服务；API 请求另设小规模并发上限，不盲目套 Promise.all。
- 本期单机回复任务可在 API 等待期间保留设备占用，简单可靠；其他设备不受影响。不要为了并行速度提前切到别的联系人，除非实现完整重入验证。
- 后续若释放占用等 API，重新获得占用后必须从定位、身份、上下文重新验证，不能保留旧焦点假设。

### 11.2 避免两个常见死锁

1. CloudPhoneTools 已有每实例 _tail 队列。不能在占着一个 `_run()` 时 await 同实例另一个需要排到其后的公开工具方法。工作流在外层组合，内部复用不重复排队的函数，或明确设计可重入边界。
2. 现有 `/api/execute` 会占 busyDevices 再 spawn 子进程。新流程不能先占该锁，再让子进程通过 HTTP 请求同一个锁；注册新入口时必须由后台任务服务直接管理，避免双重获取。

### 11.3 4318 的统一管理

建议由 4318 进程管理 AI 任务和设备仲裁；CLI 新入口调用同一个受管服务。后台未启动时明确失败，不悄悄绕过锁启动另一个控制进程。

旧脚本执行、手动控制和 AI 任务都查询同一仲裁器。用户要求接管时，任务在安全节点取消并释放；发送已派发的情况进入核验状态，不强制重置锁。

本期的受管锁不自动约束用户手工启动的旧直连 SDK/CLI 进程。文档必须说明同机不得并行运行这些未接入仲裁的入口；不能宣称已经实现全系统跨进程互斥。未来若需要，另做统一跨进程租约和失效隔离，不能只靠超时删除锁文件。

账号会话切换前停止 AI 任务，取消请求并处理不确定发送，再切换控制与数据范围；切换后禁止旧任务迟到回调继续操作。

## 12. 网页路由与操作设计

在 4318 增加以下同源路由。全部是拟新增接口，不是当前已存在的 API。

| 路由 | 用途与约束 |
| --- | --- |
| `GET /api/ai-reply/settings?deviceId=...` | 返回脱敏配置、有效 revision 和来源，不返回 Key |
| `POST /api/ai-reply/settings` | 校验并保存；携带 expectedRevision，冲突返回 409 |
| `POST /api/ai-reply/test` | 显式测试 API，不操作手机，不使用私人历史 |
| `POST /api/ai-reply/run` | 创建 plan/draft/execute 有界任务，返回 202 和 runId；不等整个长流程结束 |
| `GET /api/ai-reply/runs/<runId>` | 返回任务阶段、联系人结果、进度、错误和脱敏元数据 |
| `POST /api/ai-reply/runs/<runId>/cancel` | 幂等请求取消；取消状态不掩盖已经发生的发送 |

浏览器断开/HTTP 请求超时不代表后台任务未执行；使用 runId 查询。提交使用客户端请求 ID 防双击，同时由服务端持久化业务幂等键防重复；重试 HTTP 不新开一轮发送。

页面必要操作：保存、测试 API、生成草稿、执行一次、取消、查看结果。默认不自动执行。设备选择改变时刷新对应配置和状态，不能把上一台的 contactId 或 Key 屏蔽状态误当下一台。

草稿展示必须显示目标设备、联系人、触发消息范围和版本。将来若增加“发送此草稿”，只能提交 jobId，后台重新校验再发；不能由浏览器随意提交一段文本并借用旧身份校验结果。

## 13. 错误分类与重跑规则

| 错误/状态 | 含义 | 自动处理边界 |
| --- | --- | --- |
| CONFIG_INCOMPLETE / CONFIG_INVALID | API 或提示词配置不完整/非法 | 修正配置；不操作手机或发送 |
| DEVICE_BUSY / MANUAL_TAKEOVER | 被其他受管任务或人工占用 | 排队或退出，禁止抢锁 |
| ACCOUNT_SCOPE_CHANGED | 账号会话改变 | 终止旧任务，重新建立范围 |
| MESSAGE_LIST_UNCONFIRMED / CHAT_UNCONFIRMED | 页面未确认 | 有界重读/返回；预算耗尽停止 |
| TARGET_MISMATCH / TARGET_UNVERIFIED | 目标错误/身份不可确认 | 不写入该联系人、不输入、不发送 |
| RECOGNITION_FAILED / OCR_INCONSISTENT | 识别服务错误或读数不稳定 | 有界新鲜截图重读；不当作没有消息 |
| HISTORY_GAP / HISTORY_ALIGNMENT_AMBIGUOUS | 与存档无重叠/重复消息有多解 | 预算内补屏，否则转人工 |
| UNSUPPORTED_MESSAGE_TYPE | 关键新来信为未支持媒体 | 保存覆盖信息，转人工 |
| CONTEXT_BUDGET_EXCEEDED | 完整历史放不下 | 不悄悄裁剪；用户调整策略后再生成 |
| API_AUTH_FAILED / API_INVALID_RESPONSE | 鉴权失败/响应不符 | 不盲重试、不发送 |
| API_RATE_LIMITED / API_TIMEOUT / API_UNAVAILABLE | API 限流、超时或不可用 | 仅生成阶段按预算有限重试 |
| STALE_CONTEXT / CONFIG_CHANGED | 生成期间会话或配置改变 | 旧草稿失效，有界重读重生成 |
| DRAFT_NOT_EMPTY / INPUT_MISMATCH | 原有草稿/输入不符 | 保留现场，不清用户内容、不发送 |
| SEND_UNCERTAIN | 可能已发送但未完成核验 | 只读核验或人工处理，禁止自动重发 |
| DATABASE_FAILED | 增量或发送意图持久化失败 | 点击前则禁止点击；点击后则保留副作用不确定性 |
| TIMEOUT / ABORTED | 总预算耗尽/用户取消 | 停止新动作，释放输入状态，保留可恢复进度 |

所有重试共享 deadline 和次数上限，不能每层都重置 timeout 后无限延长。重跑时先查未完成 job 和发送核验，再决定是否读取新消息或请求新回复。

## 14. 性能要求与可观察性

- 使用常驻 GPU、已有拼音 worker 和复用控制连接，不改模型文件，不临时安装另一套 OCR。
- 同一快照可供确有需要的识别并发复用；避免一次检查无脑提交四个入口。
- 候选列表可使用 ROI/内容指纹减少重复 OCR，但动画变化不能成为永久漏扫的依据，必须保留周期性完整复查接口。
- 历史只向上追到可验证存档锚点，不每次采完整历史；数据库使用有界查询和预编译语句。
- 短事务中只做 SQL；API 等待期间不持数据库写事务。
- 等界面变化使用受限轮询/断言，不增加大量固定 sleep；不能为了速度删掉对象确认、草稿校验或发送核验。
- 日志包含 runId/jobId/operationId、设备、阶段、重试、错误码和耗时；默认不输出历史全文、系统提示词全文、API Key、云机令牌。
- 诊断截图放受控运行目录，记录引用、保留策略和隐私边界；普通任务状态接口不回传整包截图/历史。
- 实测分别报告冷启动、热调用、截图、识别排队/推理、API 首次完整响应、每字输入、发送核验、端到端耗时及样本数。不能把 GPU 推理毫秒数当作自动回复总耗时。
- 不写未经实测的“总耗时小于某秒”承诺。整体时延还受 API 和中文候选输入影响。

## 15. 分阶段执行顺序和门禁

### P0：盘点与兼容基线

1. 阅读第 2 节文件；记录当前改动、公共 API、数据库版本和相关调用方。
2. 确认 Node 支持 node:sqlite、现有环境可用；不擅自重装依赖或重启全部服务。
3. 在无真实凭据、无云机连接、无真实库的条件下执行现有相关测试，区分原有失败和新增失败。
4. 给准备提炼的发送逻辑补特征测试。保存改动前文件快照或可恢复 diff，不覆盖其他助手修改。

完成门槛：确认真实接口和测试基线，不以旧助手“73 项通过”的转述替代本次验证。

### P1：增量数据模型与纯去重算法

1. 实现迁移、归档导入、来源映射、消息序列和游标。
2. 实现纯 message-merge；区分唯一对齐、无重叠、歧义和 OCR 不一致。
3. 用临时 SQLite 验证重复导入、重复观察、真实重复发言、事务回滚、崩溃恢复。
4. 保持旧存储方法语义，确保旧流程读写不被新表破坏。

完成门槛：不接 API、不操作手机即可通过核心一致性用例。

### P2：API 配置、历史构造与纯回复

1. 实现网页配置的后台存储契约和 revision；先可用本地模拟配置测试。
2. 实现历史角色、重复内容保留、系统提示词、预算、响应和错误归一化。
3. 用本地模拟 HTTP 服务验证成功、鉴权失败、429、超时、迟到、非法响应、截断和取消。
4. 配置真实供应商后，经用户明确启动做一次不含私人数据的 API 测试。

完成门槛：实际请求携带正确系统提示词和历史；此阶段不输入手机，不发送。

### P3：候选扫描、对象核对和增量读取

1. 复用现有模型和截图，新增明确对象核对。
2. 使用脱敏/合成观察数据先验证导航和读取状态机。
3. 在用户指定设备和测试联系人上显式启动 draft 采集，验证新消息与历史对齐。
4. 先只保存和展示草稿；重复运行不得重复追加或丢失真实重复发言。

完成门槛：能明确说明“哪些是旧消息、哪些新增、为什么确定是此联系人”，歧义时会停止。

### P4：通用输入与单次发送

1. 在特征测试保护下提炼旧发送共用能力，保留 sendContact 公共行为。
2. 实现 sendChatMessage、发送意图持久化、前置重核验和己方气泡确认。
3. 模拟发送前后各个崩溃点、断连和取消，确认没有重发路径。
4. 用户明确选择测试对象并允许后，先测试输入不发送，再执行一条普通文本发送。

完成门槛：已观察己方气泡才记对应状态；任何不确定情况不会自动点第二次。

### P5：4318 页面和完整有界工作流

1. 接入设备仲裁、异步任务、配置、状态、取消和客户端防双击。
2. 新 CLI 走受管入口；注册脚本时避免 spawn/锁递归死锁。
3. 按“已有历史 → 来新消息 → 去重入库 → 请求含历史与提示词 → 打字发送 → 记录己方消息”完成单设备闭环。
4. 再测试两个设备并行，确认数据/配置隔离；本期不扩展为无限调度器。

完成门槛：网页刷新不会新发一条；后台恢复先核验未完成发送；用户取消和手动接管可控。

### P6：文档、回归与交付

1. 更新 SDK 类型、脚本列表、启动说明、配置字段、错误码、限制和恢复步骤。
2. 跑相关测试及可运行的完整离线测试；记录实际命令和结果。
3. 将 Mock、离线图片、真实 API、真实设备输入、真实发送分别列为已验证/未验证。
4. 逐文件核对 diff，确保 models、证书、云机凭据和真实历史未被意外改动。
