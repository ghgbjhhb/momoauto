# ScreenParser 聊天列表实测（2026-10-13）

## 结论

现有部署能正常推理，热启动速度够快；但当前权重在本次 4 张陌陌聊天列表截图上的元素定位不够用，不能直接用于识别并点击指定聊天对象。

模型主要把聊天区域判为一整块 `Image`，偶尔检出页面顶部按钮或底部区域，没有单独定位到用于评估的聊天头像、未读角标或聊天行。这是这组截图的实测结论，不是对所有界面或所有 ScreenParser 权重的通用准确率声明。

## 方法与范围

- 调用已经运行的本地服务 `http://localhost:8000/parse`，没有重新安装模型或修改服务。
- 服务健康检查正常，报告使用设备 `0`、55 类元素。
- 使用用户提供的 4 张真实截图：列表顶部、剪贴板遮挡、列表中段、含“最近在线”推荐区的列表。
- 裁出手机画面，去掉电脑窗口标题栏和投屏侧边工具栏，再提交给模型。原始窗口的初步推理也主要检出了外层工具栏，不能作为 App 内识别成功的依据。
- 不用 OCR，不由人工补充模型结果，不点击 App，不读取更多聊天，不发送消息。
- 人工参考框仅用于评分，不参与模型推理：共 13 个清晰聊天头像、11 个可见普通会话未读角标、14 个普通会话行实例。
- 各截图可能出现同一用户，以上数字是截图中的实例数量，不是独立用户数。
- 排除系统通知、“收到的招呼”、横排“最近在线”推荐头像、被裁断的聊天行，以及被遮挡的头像/角标。
- 命中标准为同类别预测框与参考框一对一匹配，交并比（IoU）至少 0.5。另检查了 `Image` 框是否能代替 `Avatar` 局部定位，同样没有命中。
- `List Item` 行评分只检查该类别是否直接输出行框；没有验证基于其他叶元素重新组合聊天行的算法。

## 速度

在模型已常驻的服务中，对第一张真实手机截图额外连续运行 5 次默认参数：

- 服务报告的 GPU 推理中位数：**45.15 ms**，均值 45.30 ms。
- 本地 HTTP 上传截图到收到 JSON 的请求中位数：**54.53 ms**，均值 55.34 ms。
- 首次裁剪形状的推理为 296.42 ms，该次完整请求为 322.58 ms；这是本次调用观测值，不代表每次服务启动耗时。
- 上述请求时间不含获取投屏截图、身份确认、点击、页面跳转或聊天输入；不是完整自动化流程延迟。

## 为什么不能独立完成用户识别与聊天记录

即使后续定位效果改善，ScreenParser 的输出仍是元素类别、框和置信度，不是昵称、用户 ID 或聊天文本。

[官方模型说明](https://huggingface.co/docling-project/ScreenParser)明确指出：它不输出检测元素的文字内容，且训练数据是渲染后的网页截图，对原生移动 App 等分布外画面可能存在泛化差异。本次表现与这种限制一致，但没有通过实验单独证明失败的具体原因。

要实现可靠会话记录，仍需要独立的身份来源和内容读取方式。可以评估平台允许的 Android 控件树是否提供昵称/用户信息；若拿不到控件信息，再考虑面向此 App 的元素检测训练与文字/身份识别。不能仅用固定屏幕坐标或昵称作为永久唯一 ID。
