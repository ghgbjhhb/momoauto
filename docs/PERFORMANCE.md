## 常驻识别的实现

- 四类核心队列：列表 2 路、详情 3 路、页面 2 路、OCR 2 路；核心全局执行上限 3。
- 共享范围扩大到不同 Node 进程：`src/automation/recognition-service.js` 客户端，`scripts/recognition-service.js` 服务。
- 原通用/IME RapidOCR 1.2.x + PP-OCRv3 保持不变，只把 ONNX 会话切到 CUDA；没有沿用 GPU 环境默认 v4。页面判定仍用自己的原实现及已确认的优化参数。
- OCR 检测/识别/方向分类首选 provider 均实际验证为 CUDA，预热含真实文字运算。cuDNN 使用 HEURISTIC；解码/后处理仍可能在 CPU。
- 打开 MOMO 专用进程单路常驻，独立队列，不在核心全局 3 槽内；默认核心启动后预热。拼音 Python 也预热词典。
- 当前公开默认入口、旧工作流 OCR、输入法候选 OCR、联系方式/拉黑、CLI 已连接公共服务。显式自定义视觉配置和嵌入式池仍按调用方选择运行，不强行覆盖。

启动/状态/停止及错误码见 [GPU 识别说明](GPU-RECOGNITION.md)。

## 其他实际核验

- 两个独立 Node 子进程均返回同一常驻 Python PID 84359，证明跨进程复用；关闭借用 OCR 客户端后仍可继续识别。
- 最终服务默认 9 路实例就绪，通用 OCR 的三个 provider 均为 CUDA，implementation 为 legacy-ppocr-v3；附属 MOMO 进程已常驻。
- 原模板/双 YOLO 链离线识别桌面和消息列表正常；借用启动约 1.25 ms，原算法整张处理仍有约 115–355 ms，不是改成零成本识别。
- 分词规划 4 条文字 `1，那你看好了` / `123` / `456` / `789`：旧逐次 Python 启动合计约 3584 ms；共享进程预热后实测合计 5.46 ms；均通过重拼接检查。键盘、倒计时和候选等待不在该计时内。
- 坏图、错误模式、无效 signal、提前取消、1 ms 超时分别返回 IMAGE_INVALID / INVALID_ARGUMENT / ABORTED / TIMEOUT；错误后下一张正常完成，迟到结果不会串单。
- 一次提交 40 个 OCR 请求：32 个完成、8 个 QUEUE_FULL，40 个 ID 唯一。核心预算、客户端预算和工作通道不会因调用方超时就提前视为空闲。
- 未带服务令牌访问状态端点返回 403。识别结果不写入服务日志；调用者自行保护返回的文字与截图。
- 本地内存模拟云盘/VPC 接口：并发读取保序、上限 4；一次提交后详情核验得到 6 个 ID；读取失败不发送；并发设备列表读取合并，之后新请求重新读取、结果互不共享可变对象。没有向云后台写入。
- 86 个 JavaScript 文件、16 个 Python 文件通过语法解析，无新增测试文件或测试套件。
