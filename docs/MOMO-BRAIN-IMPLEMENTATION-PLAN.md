> 日期：2026-10-19。项目：`D:\AA-project\自动化`。本文是交给开发助手的执行计划，不代表中枢已实现或通过实机测试。

> 只使用现有 `http://127.0.0.1:4318/`。本次文档编写只做源码检查，没有启动中枢、调用聊天 API、操作手机或运行测试。

## 1. 用户要求与最终运行形态

中枢负责长期运行、发现消息、协调任务和恢复页面，不是另一个生成聊天内容的大模型。聊天内容仍由已有 AI 回复工具负责。

核心要求：

1. **所有业务页面判断统一通过一个页面服务。** 不允许每个脚本对“当前在哪个页面”各自猜测。
2. **如果当前页面不在当前任务预设范围，按一次返回键，再重新截图判断。** 必要时重复，但有次数、时间和无进展上限；不是先回桌面重新打开软件。
3. 默认停留消息列表持续巡检；发现疑似来信，调用 AI 回复闭环读取、去重、带历史和提示词生成并发送。
4. 在没有待回复任务且用户开启时，安排有限的首页浏览、招呼处理；完成后返回消息列表。
5. 同一设备只能有一个操作流；多台设备可以有限并行，识别共用常驻 GPU。
6. 用户可以启动、暂停、恢复、停止、手动接管。网页关闭不终止已明确启动的后台中枢。
7. 重启能恢复计划和待办；但不确定是否已发送/已通过的动作必须先核验，不能重做。

运行主线：

```text
启动 → 检查依赖/账号/占用 → 恢复未完成任务 → 统一判断页面
                                          ↓
                              不在任务允许页：返回一次 → 重新判断
                                          ↓
                              到达消息列表 → 扫描候选新消息
                                          ↓
                       有待回复：读取/去重/AI 回复/发送核验
                       无待回复：检查空闲任务是否到期
                                          ↓
                          返回并核对消息列表 → 可取消等待 → 下一轮
```

“持续监听”指后台持续调度视觉巡检，不是已经取得平台原生消息推送。同一台手机在聊天、浏览或招呼界面时，不能同时读取消息列表；界面离开时长和实际巡检延迟必须如实记录。

### 2.2 当前源码暴露的接入门禁

编写本文时已看到以下待核对点。这不是完整审计报告，执行助手开工时必须重新检查，因为其他助手可能同时修改代码：

- `CloudPhoneDevice` 当前定义了 tools()，未看到 vision()；新 AI 工作流却调用 phone.vision()。必须接到真实存在的截图/识别接口，不能用空对象兜底掩盖。
- 新 AI 工作流扫描候选后，尚未看到“定位并点击该候选卡片进入聊天”的完整导航步骤；不能直接在列表上做聊天核验并无限重试。
- 页面/OCR/模型结果若分别各自取图，容易产生不同帧证据混用。中枢需要明确的截图快照契约。
- 旧任务和手动控制仍使用 busyDevices/独立手动占用；新 AI 模块使用 defaultArbiter，当前尚未形成同一控制边界。
- 新 AI 路由创建 AbortController，但单次工作流是否真正贯穿 signal、超时和动作前取消检查，需要验收。不能仅把 HTTP 状态标 cancelled，就认为旧任务已停止。
- 新仲裁器允许同 ownerId 重入，但没有嵌套释放计数/所有权区分。不能让子工具释放父任务仍需持有的锁。
- 现有首页/招呼工具没有中枢所需的完整持久化让出协议；不能假定已经支持 checkpoint/yield。
- AI 返回值当前包含 `status/data`、`data.ok` 和 `contactsProcessed` 等实际字段，不能机械按上一份计划的建议字段读取。需适配并统一语义。

这些问题未处理前，可以开发中枢纯逻辑、Mock 测试和观察模式，**不能开启无人值守 execute**。

## 3. 范围和系统分层

建议分四层：

```text
4318 网页 / 薄 CLI
       ↓
BrainManager：配置、会话生命周期、多设备协调
       ↓
每台设备一个 DeviceActor：任务选择、串行执行、检查点
       ↓
PageService + PageRecovery + 设备仲裁 + 任务适配器
       ↓
现有 SDK、GPU 识别、AI 回复、首页/招呼/消息存储
```

核心设计不是“多个后台循环各自操作同一台手机”，而是“一个设备执行者按优先级运行任务”。截图识别也由该执行者安排，不能有一个保活线程或监控线程偷偷发返回键。

本期不做：重新训练模型、改动模型目录、自动处理验证码、自动登录、更换代理/改机/重置、自动拉黑、自动发送联系方式、自动点赞评论关注、对外售卖用户系统。

01～10 等初始化/运维脚本不是 MOMO 的异常页面。它们占用设备时中枢必须让出，不能把高德、输入法设置页面按返回键关掉。

## 4. 统一页面服务：一个判断入口

### 4.1 建议接口与返回

新增统一门面 `observePage(deviceSession, options)`，允许传入已取得的 frame；同一阶段只取一次 SDK 高清图，按需复用给各识别入口。

建议返回以下逻辑结构。字段为待实现契约，不是当前接口已提供：

```json
{
  "ok": true,
  "snapshotId": "frame-local-id",
  "deviceId": "device-local-id",
  "accountScope": "configured-account-scope",
  "capturedAt": "2026-10-19T09:00:00.000Z",
  "generation": 7,
  "width": 720,
  "height": 1280,
  "app": "momo",
  "page": "message_list",
  "scene": "normal",
  "overlay": "none",
  "keyboard": "closed",
  "confidence": 0.93,
  "evidence": {},
  "targets": {},
  "error": null
}
```

归一化页面只描述看到的界面，不描述“应不应该点”。动作决策由任务和恢复策略负责。必要字段缺失、尺寸错误、识别服务异常时返回 ok:false，不造默认页面。

截图、识别、控件坐标必须关联 snapshotId/尺寸/generation。动作前再检查证据时效，按现有工程守则超过 1000ms 重新核验。动作后所有旧目标失效。

### 4.2 页面、场景、遮挡和键盘分开

| 维度 | 推荐值 | 说明 |
| --- | --- | --- |
| app | momo / android_launcher / other / unknown | 只有证据足够才认定桌面或其他应用 |
| page | message_list / chat_detail / home_feed / greetings / other / unknown | 主页面互斥，不能同时既是列表又是聊天 |
| scene | normal / greetings_card / greetings_list / greetings_empty / chat_settings / profile / unknown | 任务子场景，按需扩展，不靠一段关键词冒充页面 |
| overlay | none / safe_dismissible / exit_confirm / login / captcha / risk / permission / unknown | 遮挡优先处理；底层仍是列表不代表可以点击列表 |
| keyboard | open / closed / unknown | 键盘是聊天页状态，不另起一个与聊天竞争的页面枚举 |

允许不确定，禁止 `confidence ?? 1` 把缺失数据提升成高置信度。基础页面与子场景冲突时返回不确定及冲突证据，不随便选一个方便操作的状态。

### 4.3 复用与迁移原则

- page 原识别器作为基础来源；chatList、chatDetail、OCR 仅补充任务所需证据。
- 招呼必须检测到真实的通过/拒绝控件及场景依据；不能把消息列表的一行文字当招呼卡片。
- 风控、登录、权限提示需判断 UI 位置/结构和短时出现特征，不能因对方聊天正文提到“过于频繁”就全局熔断。
- 截图黑屏/解码失败/断线与真实 unknown 页面分开。没有可靠图像时不发返回键。
- 允许通过原图在内存补跑需要的模型；禁止为不同判断重新取三张图再混用。
- 页面输出和原始证据按 snapshotId 做短期缓存；控件动作后或连接变化即失效，不跨动作缓存身份或坐标。
- 逐个迁移 AI 回复、首页、招呼、联系人采集、MOMO 导航中的页面判断到此入口；不能旧逻辑和新逻辑各自控制返回。
- 模型 2 的输入框/发送按钮定位与草稿 OCR 是控件核验，不应删除；其页面前置判断统一接入 PageService，图像证据仍使用同帧。
- 统一入口可以支持其他应用的 provider，但 MOMO 的页面白名单只在 MOMO 任务中生效，不强加给旧初始化流程。

## 5. 页面白名单：全局支持范围与任务阶段分开

用户预设的核心页面：消息列表、聊天详情、首页、招呼相关页面。不是“识别到这四类之一就可以随意动作”，还必须满足当前任务阶段。

| 任务/阶段 | 允许停留 | 要求 |
| --- | --- | --- |
| 默认巡检 | 消息列表 normal，无阻挡 | 作为默认锚点；不把“马上聊”匹配页当消息列表 |
| 回复：定位 | 消息列表 | 找到当前目标的真实卡片后点击 |
| 回复：读取/生成/输入/核验 | 指定联系人的聊天详情 | 页面确认和对象确认同时成立，键盘按阶段处理 |
| 首页浏览 | 首页 | 继承现有首页和底栏控件断言，不点击正文互动 |
| 招呼任务 | 消息列表入口、招呼卡片/列表/空态 | 具体阶段允许页不同；真实按钮、空态和限频分别断言 |
| 初次采集 | 当前指定联系人的聊天或受控列表导航 | 单独有界任务，不能占据所有巡检时间 |
| 空闲等待 | 消息列表 | 等待前仍核对并记录最后观察时间 |

已知但不是目标页，优先走可靠导航边：例如首页 → 识别到底栏消息按钮 → 消息列表；聊天 → 安全返回 → 消息列表。

同样是 chat_detail，若对象不匹配，不能视为回复任务已到目标；停止该任务的业务动作并安全回到列表。没有任务归属的聊天详情，默认不生成回复，先恢复列表。

任务正在输入或发送核验时，不能由另一个“全局检查器”因为不在消息列表而发返回键。页面服务只报告事实，动作始终归当前 DeviceActor/任务所有。

## 6. 统一恢复：返回一次，再观察

### 6.1 决策顺序

每次准备执行业务动作、任务切换或恢复时遵循以下顺序：

1. 检查运行会话、取消信号、设备所有权与连接代次。没有权限不发任何导航键。
2. 若发送/通过动作结果不确定，先进入该动作核验流程，不能按返回把证据现场清掉。
3. 取得新鲜快照，调用 PageService。识别服务或截图失败则走依赖恢复，不进入 unknown→Back 分支。
4. 若出现登录、验证码、风控、未知权限或会丢失草稿的确认框，停止自动业务并转对应暂停状态。不能自动确认、授权或关闭后继续。
5. 若当前页属于当前阶段白名单，执行目标/控件核验；满足则返回 reached_target。
6. 若是已知可安全导航的页面，使用有证据的导航边，然后重新观察。
7. 若确实不在预设范围或为可读图像上的 unknown，执行一次 SDK Back，确认按键释放/发送完成，再截图重判。
8. 未到目标则在剩余预算内重复，直到成功、桌面、安全阻断、无进展或预算耗尽。

### 6.2 预算与停止条件

建议初值如下，属于开发配置，不是已经压测的性能承诺：

- `maxBackSteps=8`，可配置但有硬上限。
- `recoveryTimeoutMs=30000`，每个恢复阶段共用 deadline。
- `maxNoProgressBacks=3`；指发出并等待返回后仍无可信页面/结构进展，不因时钟或动画像素变化重置。
- `maxOpenMomoAttempts=1`：确认已到桌面且用户允许恢复启动时，才调用现有 openMomo 一次。
- 多次导航/工具失败之间保留恢复总预算与窗口计数，不能换一个函数就把返回次数清零。

到桌面立即停止继续按返回。允许启动则打开 MOMO、观察并恢复列表；一次启动仍失败就暂停此设备，不循环“桌面→打开→返回→桌面”。Android 返回会影响任务返回栈，不应假设无限 Back 只会在应用内部导航。[Android 官方任务返回栈说明](https://developer.android.com/guide/components/activities/tasks-and-back-stack)

如果已持有未知或人工草稿，不能为了回到列表而选择“丢弃”；保留现场、记录原因、等待人工。可验证属于本工具的草稿，也只能由回复恢复协议处理。

### 6.3 恢复结果

统一返回：`reached_target | launcher_reached | dependency_failed | blocked_by_guard | no_progress | budget_exhausted | cancelled`，包含最后页面、backSteps、经过页面序列、原因与截图引用。

恢复成功不代表原业务动作成功。回到列表后，重新发现任务和读取 pending，不自动重放刚才失败的发送、通过或其他有副作用动作。

## 7. 每台设备一个执行者与运行状态

### 7.1 会话状态

推荐生命周期：

```text
stopped → starting → reconciling → running
                                  ↙   ↓   ↘
                    paused_manual  cooldown  needs_review
                                  ↓
                         stopping → stopped
```

running 内再记录当前 phase：observing、recovering、scanning、replying、browsing、greetings、waiting。phase 不是另开一个异步控制线程。

- 暂停：不再接新任务；当前任务在安全点退出。发送已尝试时先保留核验状态。
- 停止：取消等待和新动作，完成输入释放，持久化未完成状态，关闭本会话自有资源。
- 恢复：重新检查账号、占用和未完成副作用，再观察页面，不接着使用暂停前坐标。
- 手动接管：优先停止自动写操作并等待释放确认，再授予交互控制；用户离开手动窗口后默认仍暂停，显式恢复才继续。
- 一台设备出错只隔离该设备；共享 GPU/API 故障则阻断对应依赖的任务，不让所有设备轮番触发同一错误。

### 7.2 单循环、单定时等待

每台设备一个可取消循环；上一轮未完成不运行下一轮。禁止 `setInterval(async () => ...)` 启动重叠巡检；定时触发只负责唤醒，不直接点击或另开一次 workflow。

循环顺序：检查状态/阻断 → 核验未完成副作用 → 获取设备执行权 → 观察/恢复页面 → 选择一个有限任务 → 执行到安全边界 → 持久化 → 归位/释放 → 等待。

没有到期任务时等待最近的 dueAt、消息巡检时刻或取消/配置变化事件。睡眠必须可取消，不在业务函数里等待七到二十分钟阻断消息处理。

定时器不是实时保证，实际执行受事件循环负载影响；必须测量实际延迟，限制过长 delay，不能把非法 delay 变成高频空转。[Node.js 定时器文档](https://nodejs.org/docs/latest-v24.x/api/timers.html)

## 8. 持续消息监听的具体策略

### 8.1 快速巡检与覆盖巡检

**快速巡检**默认从消息列表顶部观察：模型定位卡片，OCR 获取必要的昵称、摘要、未读提示，结合此前观察与持久化 pending 提取候选。

**覆盖巡检**按计划分片向下扫描，避免只看最上方几个联系人。每片受页数/时间预算约束，记录覆盖范围和恢复锚点，必要时回顶部先处理新消息。

规则：

- 未读角标、摘要变化只是候选线索，不是消息正文或已确认来信。
- 没有识别到数字不等于无未读；红点、99+、角标漏识别应支持 unknown。
- 列表同文摘要未变，也可能是再次发送相同文字；结合未读、顺序变化及有界近期联系人复查。
- 系统通知、招呼入口、广告不进入普通回复队列。保留既有模型边缘卡片过滤设置。
- 列表因来信重新排序时，旧坐标和滚动游标失效。重新定位，不点固定第 N 项。
- 首次看到联系人按 AI 工具的基线策略处理，不能把多年聊天历史当新消息。
- 同一联系人已进入聊天时，读取当前聊天尾部的新增内容；但不能假装此时也在看其他联系人列表。
- 跨页不能依据“一页没有新联系人”就断言到底；预算耗尽返回部分覆盖，不报告全列表无消息。
- 页面指纹/ROI 可以减少重复 OCR；状态栏时钟、动画不能造成无休止重复识别，也不能因画面变化小永久跳过巡检。

### 8.2 待回复任务来源

待回复来源同时包括本次候选和本地未完成记录。进入聊天清除了角标、网络断开或 API 失败后，仍需从 pending 找回联系人。

业务唯一键使用设备、accountScope、会话身份、已确认消息范围/版本。不要以昵称+正文全局去重，也不要把每一次截图都创建成一个新回复任务。

同一会话有新来信，合并尚未开始的批次或使旧草稿失效。已经 send_attempted 的任务先核验，不能直接另建发送任务。

## 9. 任务优先级与调度公平性

| 优先级 | 任务 | 规则 |
| --- | --- | --- |
| 0 | 用户停止/接管、账号失效、风控阻断 | 停止接新任务，安全退出；不抢断仍按下的手势 |
| 1 | 不确定发送/通过的核验 | 不重放副作用，不先离开证据现场 |
| 2 | 已确认的新来信回复 | 每联系人每轮有限处理；重验身份与上下文 |
| 3 | 到期消息列表快速巡检 | 达到巡检延迟门槛后必须插入，避免一人持续来信占满设备 |
| 4 | 覆盖巡检、必要的有限基线采集 | 分片执行，记录未覆盖和缺口 |
| 5 | 用户启用的招呼处理 | 仅在无待回复、无阻断且巡检新鲜时运行 |
| 6 | 用户启用的首页浏览 | 同上；不能挤占正常消息处理 |

这是带约束的优先队列，不是简单“优先级低永远没有机会”：

- 默认一次最多处理一位联系人的一个批次，然后回列表巡检；同一个人持续发消息不能使其他联系人永久饥饿。
- 选择回复按等待时间和业务优先级，不只永远取列表第一人。
- 有消息积压时，首页/招呼可以被推迟或跳过；不能因为它们到点了而强行抢走回复。
- 空闲任务错过多个周期后只补一次或跳过，不在恢复时补做十轮。
- 每个业务动作的授权、配额、页面、身份和证据仍由工具校验，中枢“排了任务”不是授权跳过校验。

## 10. AI 回复适配与结果处理

### 10.1 调用边界

中枢调用已有的有界 `runMomoAiReplyOnce()` 或经验证的同等服务。使用 maxContacts=1；传入真实设备、目标会话、运行模式、signal、deadline、配置版本和操作关联 ID。

当前按 contactName 的入参需要迁移到可靠的会话引用，或在适配层明确其昵称身份限制；不能把同名联系人当稳定 UID。

页面服务和设备会话应以依赖注入传入，供内部读取/输入复用。AI 工作流不能再私建一套页面恢复循环或不存在的 phone.vision()。

### 10.2 第一版 API 等待策略

建议先采用保守策略：一个回复闭环期间保留当前设备任务所有权，不切其他联系人；其他设备可继续工作。API 请求和输入都受单次硬 deadline 约束。

因此该设备等待 API 或打字时，消息列表巡检会延后。界面显示 replying，而不是“正在实时监听全部联系人”。应记录离开列表时长，并在任务结束后优先回列表。

若将来要在 API 等待期间切回列表，必须把生成和发送拆成可恢复阶段、保存 jobId，并在重新进入联系人后全面重验身份、上下文、草稿和配置；这是独立升级，不可简单 Promise.race 后让旧任务继续运行。

### 10.3 适配结果，不重新定义聊天去重

适配层归一化当前真实结果，包括：无新增、草稿就绪、己方气泡观察成功、需基线、历史歧义、未完成、失败、发送不确定。

- no_new_messages：记录本次覆盖和观察，不清除尚未解决的旧 pending。
- draft_ready：不标已回复；同一输入与配置未变时复用草稿，不每轮重新请求 API。
- own_bubble_observed：由回复仓储提交已处理范围，中枢只保存关联结果，不再把己方气泡复制一遍。
- uncertain：建立核验任务/人工复核，禁止从头运行回复闭环。
- needs_baseline：安排有限基线或请求人工，不每个 tick 自动完整重采。
- target mismatch/history ambiguity：暂停该会话，其他联系人可继续；账号/设备风险则按更大范围暂停。
- 生成失败：保留待回复，按 API 退避安排重试；不假装“没有消息”。

中枢不重复实现另一套正文去重、历史构造、提示词或中文候选选择。配置版本变化使旧未发送草稿失效；人工新发言或新来信出现时由回复工具的前置重核验决定下一步。

## 11. 空闲浏览与招呼：只运行有限可让出的任务

### 11.1 首页浏览

- 默认关闭，用户开启后配置间隔、时段、单次预算和每日上限。
- 进入首页前由统一页面服务和导航器到达目标；继承原有控件、刷新方式和手势规则。
- 不新增点赞、评论、关注或点击帖子。现有随机参数原样保留，不将随机操作描述为能绕过检测。
- 原浏览循环需增加可选 checkpoint/yield 接口：每个刷新/滑动完整抬手并完成后验观察后，可以安全让出。
- 一轮抽取的刷新/滚动目标与当前进度持久化；暂停后不能从头重抽并重复已执行动作。恢复时仍需重新核对首页和位置。
- 中枢要求让出时在下一安全边界返回 yielded，而不是把取消误报 completed；无中枢调用者时原有单次工具语义保持不变。
- 达到离开消息列表的软预算或巡检到期，在安全点暂停浏览、恢复列表。若还无法安全暂停，记录 overdue，不宣称已经按时巡检。

### 11.2 招呼处理

- 默认关闭。启用后仍调用 cycles=1，单轮少量处理；不使用工具内部多轮长间隔作为调度器。
- 推荐单轮 maxApproved=2 作为初始产品配置，不是平台允许速率承诺；计数和每日配额由用户设置。
- 用户若只允许“通过”而未允许“拒绝”，适配器必须明确配置不执行拒绝；不能因旧工具默认概率而在后台悄悄拒绝请求。原工具默认行为不因中枢而被全局改写。
- 每张招呼卡片处理完、按键/触点释放并完成观察后，才允许让出；不能在点击中间抢占。
- 持久化阶段与动作尝试，不能只保存卡片坐标。返回列表后卡片可能变动，恢复需重新识别；不确定是否已处理的卡片不得照旧坐标重做。
- totalApproved/totalRejected 当前表示本地动作次数，不是服务端已确认人数。配额至少按已尝试动作保守扣减，不能因未确认就无限补点。
- `data.rateLimited/outcome='rate_limited'` 是明确阻断，即使 ok:true 也不能继续下一轮。
- 通过后新出现的联系人走现有基线/增量读取规则，不因为“已通过”就自动发送开场白；本期不增加主动群发。

### 11.3 能力未就绪的降级

若旧首页/招呼工具尚不能安全让出，不得把一整个可能数分钟的调用伪装成 10 秒时间片。先关闭该空闲能力，只上线消息监听；完成 checkpoint 改造与测试后再开启。

以下是待验证的初值。所有时间都能配置并设范围，不是当前实测性能或平台风控标准。

| 配置 | 建议初值 | 语义 |

观察模式允许实际导航和读取，可能清除未读角标；它不是无副作用的 plan。可另提供 plan 只展示配置和计划，不取图、不写业务库、不调用 API。

如果提供持续 draft 模式，对同一批消息只生成一次草稿，历史/配置变化才使其失效；不能把未标已回复的同一批消息每两秒再请求一次。

使用 UTC 持久化 dueAt/cooldownUntil，时段配置明确使用哪个时区；进程内耗时与 deadline 用单调时钟。休眠唤醒、系统时钟跳变后重新核对，不突发补跑任务。每个任务的剩余预算向下传递，不能深层工具不断重置。

## 13. 设备仲裁、取消与进程边界

### 13.1 一个真正的仲裁器

扩展现有 device-arbiter，不另起 BrainLock。旧脚本、AI 路由、手动控制、新中枢都使用同一个接口。

- 中枢会话存在不代表永久占设备写锁；一个原子任务/恢复片段持有执行权，空闲等待可释放。
- 同一设备只有一个 Actor，Actor 内只有一个活动操作任务。手动接管需要先暂停会话，再获取操作权。
- 子工具借用父任务 lease 时不重新获取、不释放父 lease；独立调用者才获取和释放自己的 lease。
- lease 包含 deviceId、owner、会话 epoch/代次和可校验 token。每次发送指令前验证仍属于当前执行者，迟到回调不能继续操作。
- 不依赖“同 ownerId 重入返回 true”解决嵌套；也不能让父任务拿锁后等子进程从 HTTP 再拿同一锁。
- CloudPhoneTools 的内部 _tail 队列仍需避免嵌套 await 自己后面的任务，不能因加了外层锁而忽略内部死锁。

### 13.2 取消确认与看门狗

AbortSignal 必须贯穿等待、截图、GPU、API、输入和动作派发；cancel 请求只代表已请求停止，须在清理完成后才能报告 paused/stopped。

看门狗发现任务超时，只能触发取消、报警和隔离；**不能 Promise.race 超时后立即释放锁并开始另一个任务**，因为旧 Promise 可能仍在敲键。

等待旧操作停止确认，释放触点/按键并封禁旧 epoch 后才授予新所有者。若无法证明停止，标记 device_quarantined，拒绝新自动操作，人工处理。只关闭本任务拥有的控制资源，不停止整个共享 GPU 服务。

### 13.3 受管入口与非受管 CLI

本期后台中枢和 CLI 控制命令都通过现有 4318 管理。`start/status/pause/resume/stop` CLI 是薄 HTTP 客户端，不再另启独立长期手机控制进程。

现有其他直连 SDK/CLI 如果不接入仲裁，本期不能声称已约束它们。需要在文档和入口明确同机运行限制；强制跨进程互斥属于后续独立工程，不用删除锁文件或超时抢占假装解决。

## 14. 持久化、幂等与重启恢复

建议新增中枢控制库 `.runtime/momo-brain/control.sqlite`，只存运行配置、计划、任务引用与状态。聊天历史、AI 草稿/发送事实仍留在原设备 ReplyStore 中，不复制成另一套聊天库。

| 数据 | 必需字段/约束 |
| --- | --- |
| brain_sessions | deviceId/accountScope、sessionId、epoch、mode、desiredState、实际状态、配置 revision、停止原因 |
| brain_schedules | 下次巡检/覆盖/空闲任务 dueAt、cooldownUntil、最后结果、配额窗口 |
| brain_tasks | taskId、业务幂等键、类型、会话范围、优先级、状态、attempt、deadline、checkpoint、关联 replyJobId |
| brain_events | 有限保留的状态转换、错误、耗时、证据引用；默认不存私人全文 |

要求：

- 任务状态包含 queued/running/yielded/waiting/reconciliation_required/completed/cancelled/needs_review，不把异常任务直接重新置 queued。
- 在短事务内声明/领取任务，条件更新状态；同一业务键只允许一个有效任务意图。
- 调度 tick 不入成千上万个数据库任务；同类周期任务合并，错过多次只保留一次待办。
- 回复已保存 pending 但中枢尚未入队时崩溃，重启要扫描 ReplyStore 找回；两个数据库之间没有跨库原子事务，必须靠幂等发现/核对补齐。
- 发送事实以 ReplyStore 为准，中枢不能独立声称已回复；双库提交中断时重新核对引用。
- quotas 和 cooldown 随重启保留，不能靠重启清零。
- 迁移有版本、一致性备份和恢复步骤，不删除旧真实聊天数据。

重启顺序：取得服务单实例边界 → 读取配置和期望状态 → 核对设备/账号 → 发现非终态任务 → 优先核验发送/通过不确定性 → 处理失效计划 → 观察并恢复页面 → 用户授权或明确 autoResume 策略允许后继续。

程序关闭时停止接受新任务，取消等待，等待有界清理，持久化未完成事实。无法完成清理就保留 unclean 标志，下次先 reconciliation，不冒充所有任务正常结束。

## 15. 冷却、错误和安全阻断

区分三种来源，不能混成一个 sleep：

- **MOMO 平台频率限制/风险**：默认暂停该设备/账号范围的自动业务写操作，保存原因和冷却/人工恢复要求。不能切去浏览或招呼来规避限制，更不能下一轮立即重进。
- **聊天 API 的 429/限额**：限制对应供应商生成任务，尊重 Retry-After/配额；保留 pending，不假装没有消息。只读巡检可继续，但不得制造无限新草稿请求。
- **截图/GPU/网络故障**：暂停依赖该能力的任务并退避，不能在看不见页面时盲按返回；共享故障由管理器合并探测，避免每台设备各自高频重启服务。

建议统一错误码：

| 错误码 | 处理 |
| --- | --- |
| PAGE_OBSERVATION_FAILED / FRAME_STALE | 无可靠观察，不执行恢复按键 |
| PAGE_UNEXPECTED | 有图像但不在当前预设页，进入有界 Back 恢复 |
| RECOVERY_BACK_LIMIT / RECOVERY_NO_PROGRESS / RECOVERY_TIMEOUT | 暂停设备，保留页面路径和最后截图引用 |
| LOGIN_REQUIRED / CAPTCHA_REQUIRED / PERMISSION_REQUIRED | 人工处理，不自动填凭据或授权 |
| PLATFORM_RATE_LIMITED / PLATFORM_RISK | 持久化阻断，不做替代业务绕过 |
| TARGET_UNVERIFIED / HISTORY_AMBIGUOUS | 隔离该会话，不串人、不猜增量 |
| ACTION_UNCERTAIN | 核验任务优先，禁止重放发送/通过 |
| DEVICE_BUSY / MANUAL_TAKEOVER | 不抢占；按显式暂停/恢复规则处理 |
| TASK_CANCEL_NOT_CONFIRMED | 隔离设备，不释放给另一个自动任务 |
| ACCOUNT_SCOPE_CHANGED / LEASE_EXPIRED | 废弃旧证据、禁止旧回调动作 |
| DEPENDENCY_NOT_READY | 禁止 execute，允许配置或 Mock 开发 |
| SCAN_BUDGET_REACHED | 报部分覆盖，不等同“全列表无新消息” |

反复进入同一未知页、连续超时、累计恢复过多都应升级为 needs_review；不能保持 running 但永远自动返回重试。

| POST /api/momo-brain/resume | 先核验未完成副作用和占用，再恢复 |
| POST /api/momo-brain/stop | 请求清理停止；不能立即假报已经停止 |
| GET /api/momo-brain/status?deviceId=... | 会话/任务/页面/盲区/冷却/错误摘要 |
| GET /api/momo-brain/events?deviceId=...&after=... | 有限、脱敏的增量事件 |

启动/恢复/停止操作带客户端请求 ID 并由服务端幂等，双击和 HTTP 重试不能创建第二个 Actor。刷新页面和重新连接只查询状态，不自动启动或恢复真实操作。

沿用本地 Host/Origin 守卫，拒绝未选择设备和非法模式；设备 ID 不能采用网页排序。切换网页登录会话必须先停止相关 Actor，防止旧账号迟到请求继续控制设备。

可先使用轻量轮询展示状态；中枢生命周期不依赖浏览器 JS 定时器。浏览器页面隐藏、关闭和投屏无交互节流不应停止后端 SDK 巡检；也不允许用虚假触屏作为保活。

## 17. 性能与健康指标

- 每设备复用一个 SDK/tools/control 会话，跨设备借用现有 GPU 服务，不重复加载模型。
- 复用同帧证据、按需增补识别，限制截图字节缓存、队列、事件及诊断截图保留量。
- 空闲阶段自适应降低识别频率，但设置最长巡检间隔和覆盖巡检计划。
- 记录 GPU queueMs/predictMs、截图/解码、导航恢复、API、输入、发送核验和整次任务时长。
- `lastMessageListObservedAt` 与 `messageListBlindMs` 单独展示；正常 API 等待也计入盲区，不藏在模型平均推理速度中。
- 区分 schedulingLag、scanLatency、已在列表时发现延迟、离开列表导致的延迟；没有原生到达时间时，不能假造“消息到达至发现”的精确数字。
- 原图内容完全相同可能只是静止页面，不等于投屏卡死；结合 SDK/解码时间戳和连接健康判定 stale，不凭像素相等自动重连/返回。
- 共享服务故障不由每个 Actor 各启动一套恢复进程；只有统一管理器协调依赖恢复，不停止其他业务正在用的 GPU。
- 总任务数、每设备 pending、每会话草稿和失败重试都设上限，触顶明确 backpressure，不无限堆积或静默丢弃。
- 运行日志只记录 ID、阶段、状态和耗时，私人聊天、提示词全文、API Key、云机令牌不进普通日志。

## 19. 实施顺序与验收门禁

### B0：确认依赖和业务闭环

检查当前文件和其他助手改动；完成第 2.2 节接入核对，验证 AI 单次闭环和取消能力。相关测试先跑基线，区分已存在问题。未通过不得启动长期 execute，但可继续 Mock 开发。

### B1：统一页面契约

实现 PageService 和场景注册器，用同帧合成/脱敏数据测试所有支持页面、遮挡、冲突、识别失败和 generation 变化。保留模型与规则，不先做导航动作。

### B2：统一导航恢复

实现任务白名单、可靠导航边、一次 Back 一次观察、返回/时间/无进展上限、桌面单次启动和阻断状态。先 Mock 验证不会无限退回或丢草稿。

### B3：设备仲裁与单 Actor

统一旧脚本、手动控制、AI 与中枢占用；处理借用 lease、取消确认、旧 epoch 封禁、关闭清理。证明没有嵌套队列/锁死锁后再开放多任务。

### B4：持续观察与持久化队列

先上线 observe，只导航/扫描/归档，零聊天 API 与业务发送。实现快速/覆盖巡检、pending 恢复、进度、dueAt、幂等任务、重启恢复和队列上限。

### B5：接入 AI 回复

先持续 draft 验证同一批来信不会重复请求，再由用户明确启动单设备 execute。测试 API 等待盲区、新来信、人工回复、发送不确定、账号切换及退出恢复。所有回复仍调用已验收工具，不复刻一套发送逻辑。

### B6：空闲浏览与招呼时间片

增加向后兼容的 checkpoint/yield，先关闭业务动作测试中枢调度，再分别验证有限浏览、有限招呼与返回列表。未完成安全让出时保持对应开关不可用，不声称已支持实时抢占。

### B7：长期稳定性、网页和交付

接入网页/薄 CLI、实际状态和隐私日志。使用虚拟时钟验证长周期、冷却和重启；用户指定设备上做持续运行实测，记录真实时长、设备数、消息数、恢复次数、盲区、资源增长和未验证项。

先单机、后多机；压力测试使用模拟 API/控制和脱敏图，不对真人批量发送来制造负载。不能用 Mock 跑一万轮代替真机数小时验证。
